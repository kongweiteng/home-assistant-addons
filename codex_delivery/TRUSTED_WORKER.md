# Proposed trusted browser worker contract

This is an integration contract with a locally tested candidate, not a production installation. It keeps the VM owner responsive while the existing synchronous public fetch broker performs DNS or HTTP.

The main execution process creates the VM directly and retains its pidfd. Each browser operation starts at most one fixed trusted broker subprocess, lazily on its first fetch, with a fixed image-owned module and bounded IPC. No Python `preexec_fn` runs in the multithreaded service. The fixed worker entrypoint pins its expected parent, sets irreversible parent-death SIGKILL and no-new-privileges, then installs hard AS256MiB/NPROC4/CPU30s/FD32/file8MiB/core0 and at most two logical CPUs before importing the HTTP broker. No credential environment is inherited. The exact policy and code digest belong to the root-owned deployment.

Only the authenticated, validated public grant and public request data cross into the broker worker. No callback credentials, lease tokens, database, workspace, account profile or private task input enter that worker or the browser VM. The subprocess always constructs the real `PublicFetchBroker`; callers cannot select a module, executable, resolver or broker implementation.

The main process accepts one inflight request at a time, checks the grant before dispatch and after the bounded response, and waits using nonblocking IPC with short polling of cancellation and lease state. The worker cannot return a replacement grant or widen the exact URL set. Frames, per-resource/total body bytes, request count and stderr are bounded. A failed or unresponsive worker never causes a new worker or thread to start automatically.

Every fetch also has an independent owner deadline of at most eight seconds, covering worker startup, DNS, headers, body and IPC. Progress never extends it, and cancellation or original-grant expiry takes precedence. At this deadline the owner closes dispatch permanently, kills through the retained worker pidfd and confirms termination; an unconfirmed stop remains uncertain. Only this fixed worker selects `PublicFetchBroker(owner_deadline=True)` to omit its internal Timer thread. Other broker callers retain their previous Timer behavior. This avoids allocating a thread under shared-UID RLIMIT_NPROC accounting: target-kernel HTTP qualification exposed Timer startup failure when unrelated processes already occupied the same UID budget. Raising the worker limit does not address the accounting mismatch and is not used.

Cancellation, lease loss and deadline expiry first revoke the local operation grant and close its dispatch gate. The main process then sends stop through the retained worker and VM pidfds and confirms both ended before reporting a settled cancellation or accepting another operation. Killing the worker prevents a delayed DNS answer from returning to userspace and opening a later connection. A request already sent before cancellation cannot be recalled; its late response is discarded. Unconfirmed stop produces `uncertain`, with no checkpoint or success receipt. A completed result is committed only after the broker and VM are both confirmed stopped and the original task lease remains valid.

`browse(..., cancelled=callback)` polls a nonblocking, side-effect-free task-state callback during broker IPC, VM output, and writes. The first true value permanently revokes that grant for its remaining lifetime. A cleanup failure freezes the backend and retains owner handles for diagnosis; another browse cannot start. There is no worker/thread replacement on error. The same original grant remains subject to its wall-clock and monotonic expiry. Fixed Linux tests with two extra same-UID processes cover two successful HTTP reads through one worker without Cookie/Authorization, blocked DNS, actual HTTP-body cancellation, and continuously dripping headers/body that must obey both the owner deadline and earlier cancellation. They confirm worker stop, closed dispatch without replacement and no late resolver return. A real native VM test additionally confirms both worker and VM stop during a blocked resolver and refuses reuse of the cancelled grant. Complete target HA qualification of the corrected HTTP strategy and production service integration remain separate gates.

The native launcher must bind a supplied expected parent PID before untrusted execution. It checks the actual parent against that value before and after installing irreversible parent-death SIGKILL. If the creator dies between fork/exec and launcher startup, the launcher must reject adoption by PID 1 and never start QEMU. The VM must never be created inside the broker worker: keeping VM creation and pidfd ownership in the main process avoids an unregistered VM window. Parent-death behavior, cancellation while DNS is blocked, cancellation while HTTP is blocked, late-response rejection and no replacement-worker behavior require fixed real-process tests before integration.

The independent `native-resource-v1` policy uses explicit `native_address_overhead_bytes`, `native_max_address_bytes`, `native_max_threads` and `native_cpu_count`. A VM's hard AS budget is its guest memory plus the address overhead, bounded by the native maximum and the inherited hard limit. `max_host_memory_bytes` retains its cgroup-memory meaning. Native thread accounting is UID/ucount based and is not described as per-task PIDs. Fixed CPU affinity limits simultaneous logical CPUs and is not represented as an average cgroup quota. Trusted parent budgets are separate; cumulative RLIMIT_CPU must not be applied as a per-operation limit to a long-lived HTTP service.
