# Fixed OCI assembly candidate

This local candidate assembles an OCI image from an administrator-fixed base and exact sealed Git candidate. It executes no source, Dockerfile, shell, package installer or build hook. Python and Node service profiles only copy regular source files below `/app` and install a fixed interpreter command. Python uses isolated mode with a fixed `runpy` launcher that adds only `/app` for sibling module imports. Dependencies must already exist in the approved base. The runtime UID is 65532; writable data provisioning is a separate target concern.

The assembler verifies the original canonical software manifest, all source/candidate bundle digests, candidate ancestry and exact Git objects without checkout. Base archive, manifest, architecture, source prefix, repository, permissions and qualification are fixed by the recipe. A single-platform OCI graph and every uncompressed layer digest are checked under finite limits. Generated archives and receipts are deterministic and retained under an exclusive one-attempt claim. A new process can reconstruct and compare the complete artifact using only retained evidence and a disposable Git object quarantine; it does not change the retained evidence. Incomplete or changed evidence fails closed and never rebuilds automatically.

The result is `ArtifactBuildEvidence`, with **artifact blob, config and manifest digests**. It is deliberately not a `BuildObservation`: offline digests do not prove HA's actual Engine identity, target consumption, runtime health, or Release7 qualification. No Docker socket, importer, server, main wiring, credentials or deployment are included. A separately authorized constrained importer plus proof of Supervisor consuming the exact imported artifact is still required for production integration. Restart only observes; an incomplete claim requires administrative resolution.

The output/evidence directory is a local private retention store, not an off-device confirmation. Production integration must seal the artifact and retained evidence through the existing encrypted ObjectArchive, read them back independently, and bind that receipt before publishing a release. The configured qualification digest records the selected recipe's identity; it does not certify that its base contains a working interpreter or that the target can run it. Those require actual architecture/runtime qualification.

Accepted bases are uncompressed OCI image-layout tar files with exactly one image manifest and gzip or uncompressed layers, optionally carrying one matching Docker `manifest.json`. Multi-platform indexes, remote descriptors, zstd, links in the outer archive, unreferenced blobs and oversized images fail closed. Base filesystem layers are trusted image content and are never extracted onto the host.

The separate `ha-canary-python-v1` candidate requires an explicit exact `target_ref`. It preserves only that disposable canary's original root UID and private marker behavior, adds fixed Supervisor version/architecture labels and injects original sealed source/version metadata. It is for the independent upgrade/fault/restore fixture only, and adds no host capabilities. General Python/Node service profiles remain UID 65532. See the separate registry candidate's `canary-template/`; no live canary is changed here.
