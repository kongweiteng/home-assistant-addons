# Immutable loopback registry candidate

The existing Supervisor update operation cannot consume a locally loaded image reliably: DockerApp.update calls install, which either builds the store context or pulls the store image/version. This candidate supplies a real OCI Distribution repository without giving another process Docker write access.

The frozen candidate target is an independent canary. Its proposed metadata has `image: 127.0.0.1:5079/codex-work/{arch}-canary` and a unique immutable version. Supervisor expands `{arch}`, selects the store version, and pulls this exact repository/tag. The registry never accepts overwrites, redirects, upload sessions, catalog queries or Docker commands. Registry bytes are not runtime acceptance; the separate runtime Observer must see the same repository digest after Supervisor pulls and starts the canary.

Official source inspection on 2026-10-29: Supervisor `validate.py` blob `4c150c0f00a932d455c25b8e6aa0d838ff9d0171`, lines 73-105, explicitly permits registry ports and rejects tags in the image path. `apps/model.py` blob `b170164f51333b8413464278203e15c7dc2b54b8`, lines 929-940, formats the image with the selected architecture; `need_build` is false when `image` exists. `docker/interface.py` blob `f40d9c16555733bde6485c5d58e029e62b167bd7` pulls image plus version in install and calls install from update. These inspected official main sources are not proof about the deployed Supervisor. Docker's treatment of loopback HTTP registries and the deployed Supervisor's pull behavior require isolated real acceptance before enabling.

Publication needs a separate authority Ed25519 signature over the exact target, instance, slug, repository, immutable version, architecture, artifact/config/manifest/graph digests, original request/source/recipe/context evidence, permissions, qualification, confirmed encrypted archive receipt digest, grant identity and expiry. The writer receives only a scoped bearer. The registry has only the public verification key; it cannot mint grants. No task-supplied policy, filesystem path, URL, key, namespace or Dockerfile is accepted. Administrator bindings freeze recipe/permissions/qualification in addition to target identity. Grants may be preloaded or registered through authenticated POST `/internal/v1/grants`; this accepts only independently signed envelopes within those existing bindings and cannot register a target, policy, namespace or permission.

Grant registration is serialized by a private flock, exclusive and fsynced; grant identity and repository/version are unique across restart/processes. GET `/internal/v1/grants/<grant_ref>` is a separate reader-only observation. Unknown registration is never resubmitted automatically. An incomplete registration record remains observable as unknown and blocks all further writes until administrator resolution. It is never repaired, removed or replaced by startup. The complete registered envelope must equal the issuer's original before publication proceeds. No signing key or Release7 is needed by this endpoint, avoiding the initial import/Release cycle.

Publication writes and fsyncs a claim before the sole write attempt, checks the exact artifact and complete OCI graph, then fsyncs all blobs and publishes the completion receipt last. The repository/version slot is exclusive across grants and processes. After crash, existing claims permit observation only; absent or partial evidence remains unknown, never authorizing redispatch. Completed manifests remain readable after grant expiry for rollback. Revoking write/read bearers stops their respective APIs; removing the grant or stopping the service revokes access. No automatic deletion or expiry cleanup exists.

Independent readback fetches the actual version manifest, digest manifest, config and every layer through HTTP, recomputes all raw/diff digests and the graph digest, then rereads the version manifest for drift. Only this real repository observation can return `oci_repo_digest`; an offline manifest hash remains only an artifact fact. The observer uses a different bearer and never invokes publish. Production additionally needs original source reconstruction, actual ObjectArchive readback, trusted pipeline/main wiring and the independent runtime Observer's separate registration for this fixed target. A signature records an authorization; it does not replace those facts.

Proposed new permission: this registry alone would use HA host networking, with Distribution reads on `127.0.0.1:5079` only and a separate bearer-authenticated publication/readback listener bound to the exact administrator-measured Docker bridge host IPv4 on port 5080. Wildcard, LAN interface and public binds are rejected. This bridge address must be measured and approved at deployment; it is not hard-coded here. The service uses the fixed container UID 0, private 0700 directories and 0600 single-link files. Every ancestor is pinned with openat/O_NOFOLLOW and checked for ownership and unsafe writes; file reads compare before/after fstat and the directory entry identity. The original Delivery and other execution components gain no Docker socket or host network. Current public metadata keeps host networking disabled. No registry is deployed by this change.

HTTP is strictly HTTP/1.1 with one exact bound Host authority. Duplicate Host/Auth/Content-Length/Content-Type, any Transfer-Encoding and bodies on reads fail closed. Headers have a total 5-second deadline, a 16 KiB aggregate/4 KiB line budget and at most 32 fields. Each listener accepts two active connections; complete operations have a 120-second ceiling. HEAD returns the same digest/length and no body. Range is explicitly unsupported (416); resumable, chunked and redirect transports are not advertised. Clients enforce the original aggregate deadline, finite Content-Length and unique response headers without proxy, redirect or retry.

Actual local Docker Desktop testing found that its existing `127.0.0.0/8` insecure classification did not fall back from HTTPS to a plaintext listener. The candidate therefore serves loopback Distribution over TLS 1.2+ with a fresh per-process self-signed certificate; its key is loaded from a private volatile `/run` directory and the temporary files are removed before listening. The Engine must already treat loopback as insecure: the certificate is not a trusted peer identity, no CA is installed and no daemon setting is changed. TLS handshakes consume an admitted connection slot and have a three-second deadline before the separate header deadline. The bridge bearer API remains its fixed internal HTTP origin.

On 2026-10-29 a disposable local Engine fixture pulled the real source-built OCI image through this loopback self-signed TLS approach and `image.inspect.RepoDigests` matched the exact served repository manifest. The fixture had no host network, socket, capabilities or writable host mount; its temporary container, pulled image tag and key files were removed. It did not run the target image, use Supervisor or change HA. HA's actual loopback classification, TLS pull and exact runtime consumption remain acceptance gates; local success must not enable production automatically.

Rollback: stop the registry, disable/remove its approved host-network override and replace/revoke both API bearers before a later restart; restore the prior independent-canary metadata/version using its separately verified backup. Retain signed registrations, sealed artifacts and claims for reconciliation. Never remove a running service's required image or overwrite a tag. Existing production Add-ons, Core, Supervisor, accounts, firewall and registry daemon settings are outside this candidate.
