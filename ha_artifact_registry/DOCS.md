# Startup and contracts

Public metadata deliberately sets `host_network: false`, `docker_api: false` and both HA/Supervisor APIs false. Do not enable this candidate until the separately reviewed host-network permission and isolated pull acceptance are complete. It has no Docker client or socket path.

## Local packaging gate

The Dockerfile fixes the reviewed Debian base digests for Docker `amd64` and `arm64` (HA metadata calls the latter `aarch64`). BuildKit's `TARGETARCH` selects the matching stage; the Dockerfile does not consume Supervisor's `BUILD_FROM` fallback. There is no `build.yaml`: Supervisor 2026.10.5 rejected digest-form `build_from` values during a separate add-on's installation. Registry still requires its own HA build acceptance. Both the build context and image COPY admit only the six reviewed production Python modules and the startup script. Production imports require only the standard library and Debian's `python3-cryptography`; Delivery sources, task code, Docker clients and secrets are not copied.

Base digests are fixed; APT package versions and transitive dependencies are not locked, so this is not a byte-reproducible dependency build. APT uses HTTPS, zero retries, a 15-second download timeout and outer 240/360-second update/install limits. The 2026-10-31 local `linux/amd64` and `linux/arm64` builds succeeded with a deliberately invalid `BUILD_FROM` argument, using existing cached APT installation layers. This does not prove a fresh network download or Supervisor build. Each image passed seven packaging checks, including six-module source hashes, actual architecture, cryptography imports/Ed25519 verification, missing-policy refusal and disposable disabled-policy startup/SIGTERM with no listeners. Containers used no network, no host mounts, a read-only root, dropped capabilities and a private disposable `/data` tmpfs. The thirty existing Registry functional tests also passed locally.

From the repository root, run `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=.:tests python3 -m unittest test_ha_artifact_registry_packaging`. To include the three container checks rather than skip them, set `REGISTRY_PACKAGING_IMAGE` to the exact locally built image and `REGISTRY_PACKAGING_PLATFORM` to `linux/amd64` or `linux/arm64`. Build both architectures separately with `docker build --platform <platform> -t <local-image> ha_artifact_registry`. These commands create local candidate images and disposable containers only; they do not qualify publication, HA deployment, recovery or a full release chain.

## Pending network permission

The still-unapproved production change is `host_network: true` for this Registry alone. Intended application listeners are TLS read-only Distribution on `127.0.0.1:5079` and the separate reader/writer bearer API on the administrator-measured HA `hassio` bridge host IPv4 at port 5080. This grants the process the host network namespace; the fixed interfaces, ports, methods and authorization are application restrictions, not a kernel firewall. No wildcard/LAN/public bind, host-port mapping, Docker socket, Docker API, Supervisor API or Home Assistant API is requested. `boot: manual` and all API flags remain unchanged. Actual bridge identity, host listener inspection, exact Engine/Supervisor TLS pull, authorization denial, restart and revoke/rollback acceptance must be completed under separately approved deployment scope. Disabling the service/removing the private network overlay and revoking its API credentials are the rollback; immutable claims must not be deleted or republished.

Startup reads only `/data/registry-policy.json`, a regular 0600 single-link file under a 0700 Add-on data directory, all owned by the fixed runtime UID 0. Full ancestors are opened with openat/O_NOFOLLOW, checked for ownership/unsafe writes, and file reads compare before/after fstat plus the linked identity. Unsafe owners, hardlinks, symlink ancestors or concurrent changes fail closed. It accepts exactly `version: 1`, `enabled` (boolean), `docker_bridge_host` (the measured HA Docker bridge IPv4), `public_key` (base64 Ed25519 public key), distinct `writer_token` and `reader_token`, `bindings` and signed `grants`. Tokens are 32–256 ASCII non-whitespace characters, supplied through approved private runtime injection and independently registered secret indexes. The signing private key is never mounted into this service. Ordinary logs show only a generic ready/disabled/unavailable message.

Each binding has exactly `target_ref`, `instance_ref`, `slug`, `repository` (`codex-work/amd64-canary` or `codex-work/aarch64-canary`), `architecture` (`amd64` or `arm64`), `recipe_digest`, `permissions_digest` and `qualification_digest`. Each signed envelope has exactly `grant` and base64 `signature`. The canonical UTF-8 JSON grant fields are defined in `service.GRANT_FIELDS`; signatures cover all of them. A grant lasts at most 24 hours. The target/recipe/permission/qualification bindings cannot change through the API. A separate authority may sign a new exact version/source/artifact grant within those fixed bindings. There is no signing endpoint and the service cannot mint authorization.

Enabled startup verifies `/sys/class/net/hassio/bridge` and reads the fixed `hassio` interface's IPv4 with a read-only ioctl. It refuses a missing interface or any mismatch with `docker_bridge_host`; this prevents substituting a private LAN interface. It binds TLS Distribution reads only to `127.0.0.1:5079` and a separate authenticated HTTP API only to that exact bridge IPv4 on port 5080. No wildcard bind, proxy, redirect, daemon registry setting or firewall change exists. Loopback TLS uses a fresh self-signed per-process key: private volatile `/run` files are unlinked immediately after SSL loads them. No account credential, persistent key or CA is provisioned. This needs the Engine's already-existing loopback-insecure classification; the certificate is protocol transport, not trusted peer authentication. Interfaces, loopback classification, exact TLS pull and Supervisor behavior must still be observed on HA before deployment. Disabled mode opens no listeners.

The loopback API supports `GET`/`HEAD /v2/`, `GET`/`HEAD /v2/<registered-repository>/manifests/<immutable-version-or-digest>` and `GET`/`HEAD /v2/<registered-repository>/blobs/<sha256>`. It has no bearer because it is host-loopback only. The bridge API exposes those same reads under the separate reader bearer, plus reader-only `GET /internal/v1/publications/<grant_ref>` and `GET /internal/v1/grants/<grant_ref>`. The writer bearer can only register a fully signed envelope with `POST /internal/v1/grants` (`application/json`, 64 KiB maximum), or publish `POST /internal/v1/publications/<grant_ref>` with `Content-Type: application/x-tar`, one exact bounded Content-Length and the signed artifact's original bytes. Upload sessions, PUT, PATCH, DELETE, catalog, tag listing, arbitrary paths, query strings, percent encoding and unknown repositories fail closed.

`PublicationClient.register(envelope, deadline=...)` and `publish(grant_ref, artifact, deadline=...)` each issue one POST and never retry. Unknown registration uses only the original grant's GET observation. Registration records are immutable in `/data/registry/.grants`, unique by grant and repository/version, and guarded by a private flock; malformed/incomplete records block further writes. `RegistryObserver` takes its own public key/binding and may start with `grants=()`. `bind(original_signed_envelope)` verifies only the issuer's original locally. `observe_grant(grant_ref, deadline=...)` only GETs and independently verifies the server's signed original; the caller must compare it exactly before proceeding. It does not implicitly bind a server response. `observe(grant_ref, deadline=...)` reads actual immutable/version manifests, config and all layers, verifies compressed graph/expanded diff IDs, fixed runtime labels and sealed source/version metadata, and rereads the version manifest for drift. Its real repository observation uses `127.0.0.1:5079/<repository>@<manifest digest>`, independent from upload's response. This proves repository availability/content, not a pulled Engine image or running service.

All HTTP requests require HTTP/1.1 and exactly one Host matching the bound listener. Duplicate security/framing headers, Transfer-Encoding and request bodies on GET/HEAD fail closed. Headers have a five-second aggregate deadline, 16 KiB total/4 KiB per-line budget and at most 32 fields. Each listener admits two connections; each operation has a 120-second ceiling. HEAD has no body and reports the actual digest/length. Range is rejected with 416; clients must issue a complete read. No redirects, proxies, chunking or automatic retries are used by the trusted clients.

The loopback TLS handshake additionally has a three-second deadline inside one of the two admitted connection slots. To reproduce local Engine protocol acceptance after building the candidate image, run `PYTHONPATH=.:tests python3 ha_artifact_registry/tools/local_engine_fixture.py --loopback-tls` from the repository root. The helper refuses a non-local Docker Desktop context or a pre-existing target tag, publishes only disposable fixture data and pulls without running the target. It cleans only its own container/tag. This check does not qualify HA, Supervisor, runtime dependencies, archive recovery or a production grant issuer.

Local retention is `/data/registry/<sha256(repository,version)>`, 0700 with 0600 files. Every file is exclusive-create and fsynced; `ready.json` is last. A crash leaves an immutable claimed slot and `state: unknown`, never an upload permission. Existing slots are observed without overwriting any byte. No automatic cleanup or deletion exists. Signed archive receipt digests bind the authorized grant; the trusted upstream issuer/pipeline must actually decrypt and read back the corresponding existing ObjectArchive before signing/using a production grant. This candidate neither fabricates that receipt nor provides an off-device backup backend.

The complete source-to-release integration still needs the trusted issuer, concrete encrypted artifact archive readback, original source reconstruction and main wiring. The existing runtime Artifact Observer must explicitly register the selected independent target and prove the pulled RepoDigest; no additional target registration is implied by this code. [DESIGN.md](DESIGN.md) describes revocation and rollback.
